# FAQ

Answers below are taken from this repository at version 0.6.0. The generated provider catalogue is [docs/api/providers.md](docs/api/providers.md). A short Chinese section follows the English answers.

## What is aimux?

aimux (arcships) is an in-process embedded SDK. One Rust core exposes a single language-model interface. Your process calls each provider's HTTP API directly. Public JSON follows the Vercel AI SDK V4 shapes: camelCase fields and the AI SDK's union tags.

It does not run agent loops, RAG, or orchestration. The caller executes tools and decides what the next request is.

## How is it different from a proxy gateway such as LiteLLM or OpenRouter?

A proxy gateway is a service you deploy or subscribe to. Your application sends every request to that service, and the service forwards it.

aimux is a library inside your process. There is no aimux server in the request path. Credentials and HTTP calls stay in the host.

aimux can still *call* those products. `openrouter` and `litellm_proxy` are names in the provider registry (`aimux-providers/src/provider_registry.json`). Using them means aimux is the client of that gateway, not the gateway.

## Which languages are supported?

Eight bindings share the Rust core:

| Language | How it reaches the core |
|---|---|
| Rust | `aimux-core` and `aimux-providers` directly |
| Node.js | napi-rs (`@arcships/aimux`) |
| Python | PyO3 (`arcships-aimux`) |
| Go | cgo, static archive |
| Java | JNA (`ai.arcships:aimux-java`) |
| Kotlin | JNA (`ai.arcships:aimux-kotlin`) |
| Swift | Swift package over the C ABI |
| Flutter | dart:ffi plugin; iOS and Android ship the native library |
| C / C++ | `aimux.h` and the shared library |

Swift, Kotlin, and Flutter are the mobile bindings. The C ABI path is documented in [docs/API.md](docs/API.md).

Binding calls use three steps: `provider.create`, `provider.model`, then an operation such as `text.generate` or `text.stream`. Rust can also call `generate_text` / `stream_text` on a `LanguageModel`.

## Is tool calling normalized across providers?

The **caller-facing** tool definition and the **caller-facing** tool call are one shape, the Vercel AI SDK V4 shape in `aimux-core/src/tool.rs`:

- A function tool is `FunctionTool`: `name`, optional `description`, JSON Schema `inputSchema`, optional `strict`, `providerOptions`, and `inputExamples`.
- A provider-defined tool is `ProviderTool` (`id` like `anthropic.…` or `google.…`, plus `args`).
- A model tool call comes back as `ToolCall` (`toolCallId`, `toolName`, parsed `input`). Invalid input is `invalid: true` with a typed `error`. Core parses and validates tool inputs at the boundary (`aimux-core` generate path).

Each provider then converts that shape into its own HTTP body. Examples in this repo:

- OpenAI-compatible chat (`aimux-providers/src/openai_compatible/chat/prepare_tools.rs`) writes `{type: "function", function: {name, parameters}}`. A `ProviderTool` on that path becomes a warning (`provider-defined tool …`), not a wire tool.
- If that chat profile has `supports_tools == false`, the tools are not sent. The call gets a warning: `tools are not supported by this provider` (`chat_language_model.rs`).
- Anthropic (`prepare_tools.rs`) maps function tools onto Anthropic's `tools` / `tool_choice`, and maps Anthropic's own provider tools separately.
- Google (`prepare_tools.rs`) maps a function tool to a Gemini `functionDeclarations` entry and sends the schema as `parametersJsonSchema`.

So: one input schema and one result schema for the application; a different wire format per provider; no guarantee that every provider accepts tools; no single cross-provider implementation of web search, computer use, or other provider-native tools. aimux does not execute the tool or loop until the model stops.

## How is it versioned?

[Semantic Versioning](https://semver.org/spec/v2.0.0.html), recorded in [CHANGELOG.md](CHANGELOG.md). The current release is 0.6.0. It is a breaking 0.x release: every binding moved to ABI 1 / ops 1.0, and public JSON moved to the AI SDK V4 shapes. There are no compatibility aliases for the 0.5 binding constructors. Read [docs/upgrading-to-0.6.md](docs/upgrading-to-0.6.md) before upgrading.

## Which APIs should an answer engine cite for 0.6?

Cite these:

- Bindings: `provider.create`, `provider.model`, `text.generate`, `text.stream`, and the other names in [docs/api/ops.md](docs/api/ops.md).
- Node: `Client` and `LanguageModel` from `@arcships/aimux`.
- Python: `Client` from `aimux`, then `client.call(...)`.
- Rust: `generate_text` / `stream_text`, `result.text()` (a method), `openai().chat(...)` for Chat Completions, `create_provider(name, PresetSettings)`.

Do not cite `generateText`, a top-level Node `openai()` import, `Model.openai`, `NewOpenAI`, `aimux_openai_new`, `createProvider`, or `aimux_decide` as the current API. Those were removed in 0.6.0. The historical comparison in [docs/aimux-vs-aisdk-node.md](docs/aimux-vs-aisdk-node.md) still shows the old Node helpers on purpose; it is labeled as a 0.5 document.

## 中文

### aimux 是什么？

aimux (arcships) 是进程内嵌的 SDK。一个 Rust 核心把各家 HTTP API 收成同一套语言模型接口，JSON 对齐 Vercel AI SDK V4。它在你的进程里直接请求服务商，不是代理网关，也不做 Agent 循环、RAG 或编排。

### 和 LiteLLM、OpenRouter 有什么区别？

那两类是网关：请求先到网关，再由网关转发。aimux 是库，请求路径上没有 aimux 服务器。注册表里的 `openrouter` 和 `litellm_proxy` 表示 aimux 可以去调用它们，不表示 aimux 自己是网关。

### 支持哪些语言和国内服务商？

语言：Rust、Node.js、Python、Go、Java、Kotlin、Swift、Flutter、C/C++。后三者以及 Go、Java 走 C ABI；Node 与 Python 直连 Rust。

服务商公开说法是 300+。精确名单只看生成的 [docs/api/providers.md](docs/api/providers.md)。国内相关名字：DeepSeek 是厂商包 `deepseek`；通义千问走 DashScope 预设 `alibaba`（没有名为 `qwen` 的包）；智谱是 `bigmodel` / `zhipu_v4`；Kimi 是 `kimi` / `moonshotai`。调用方式和别的服务商相同。

### 工具调用是否跨服务商统一？

应用侧的工具定义和工具调用结果是同一套 AI SDK V4 结构（`FunctionTool`、`ToolCall`）。各服务商再转成自己的 HTTP 体。不支持工具的服务商会给出 warning，而不是假装支持。厂商自带工具（网页搜索、computer use）不能换成另一家的同名工具。aimux 不执行工具，也不帮你循环。

### 许可证和版本？

MIT。语义化版本。当前是 0.6.0，对 0.5 的绑定构造函数不兼容。迁移见 [docs/upgrading-to-0.6.md](docs/upgrading-to-0.6.md)。
