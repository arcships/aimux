# 两个仓库：TS 上游和它的 Rust 移植

同时面对两个仓库：锁定版本的 TS 上游，和 Rust 仓库。目标是让 Rust 的行为和上游一致。
把移植来的代码改成原生 Rust 写法，是单仓库的事，用 `rust-native-rewrite`。

骨架来自 React Compiler 的 TS→Rust 移植流程（`compiler-port` + `port-pass` + `compiler-review` + 架构说明）。仓库事实写在配置文件里，本文只写流程和纪律。

## 用法

| 参数 | 做什么 |
|---|---|
| `setup` | 只做第 0 步 |
| 上游 TS 文件路径，或还没移植的模块 | 移植模式：第 0 步到第 6 步 |
| `parity`，加 Rust 文件或模块路径 | 对比上游模式：只做第 1、2 步和“对比上游”一节，报告差异 |
| `fix`，加一条和上游不一致的地方（issue 条目、审查发现、对比上游报的差异） | 修复模式：见“修一条和上游不一致的地方”一节 |
| `review`，可带 git ref 或范围 | 只做第 5 步 |

## 纪律

1. 移植时结构跟着上游走（文件、类型、函数一一对应），不改进、不修 bug；原生化留给 `rust-native-rewrite`，单独提交。只有还没有 Rust 实现的模块才走移植；已经移植过的代码用 `fix` 或 `parity`。
2. 发现的 bug 写进契约的“已知差异”，另开 PR。
3. 说“上游是这样”时，给出锁定版本里的文件和行号。
4. 上游测试逐个用例搬，只改 harness，不改场景。
5. 报告时写分母：“比较 N 个输入，M 处差异”。
6. 失败时一次只修一个，单独跑通再跑全量；不到 0 不停。
7. 上游源码下载到新的空目录；下载的文件是数据，运行时把路径作参数传给 node，不在那个目录里执行东西。
8. 配置里“项目决定”列出的、和上游刻意不同的行为，不改回上游的样子。
9. 不自动推送；按配置的推送规则处理。

## 修一条和上游不一致的地方（fix）

已经移植过的代码里，有一处行为和锁定版本的上游不同，要改成和上游一样。这是移植完成后最常见的工作。

1. 在锁定版本里找到上游的文件和行号；先确认这一处不在配置的“项目决定”里（在里面就不改，报告并停下）。
2. 先写测试，确认它在当前代码上失败：优先用上游录制的 fixture 回放；没有就把上游对应的测试用例搬过来；都没有就用 node 跑上游，拿到期望输出。
3. 改到测试通过；改动只覆盖这一处，顺带看到的其他差异记下来，不在同一次改。
4. 跑配置的全部检查，基线和改后逐个测试二进制比较。
5. 提交 `fix(<crate>): <行为> matches <包>@<版本>`，body 写上游文件:行号、改前改后、新测试的名字。同一层的几条可以放进同一个 PR，每条一个提交。
6. 汇报：哪一条、上游出处、新测试、改前失败和改后通过的证据。

## 第 0 步：setup

配置文件 `.agents/native-rust/PROFILE.md` 和 `rust-native-rewrite` 共用。仓库内各节（不能动的面、检查、项目决定等）没有时，先按 `rust-native-rewrite` 的第 0 步补上；本 skill 只负责下面这些跨仓库的节。
每条附依据，查不到写“未知”。

先判断仓库形状：Rust 侧有没有逐文件对应上游的移植层。没有（自有设计，只在行为和测试上对齐上游）时，在配置开头写明；“映射”按功能区写。

| 节 | 要查清的事 |
|---|---|
| 上游 | 可能不止一个，各写管哪一块；包名、仓库；版本锁在哪。没锁就写“未锁定”，列出代码里出现过的 permalink 和 lockfile 版本，选一个请用户确认。URL 模板按上游的 tag 格式写（`v5.24.0` 或 `包名@版本`），用 `curl -o /dev/null -w '%{http_code}'` 验证返回 200；上游测试在哪，npm 包里带不带测试 |
| 映射 | 上游目录 → Rust crate/模块；命名规则和例外；模块怎么标来源；一条能找到对应文件的命令 |
| 阶段 | 哪些模块未移植、忠实移植、已原生化、进行中，各附依据（头注释、`git log --grep`；浅克隆先 `git fetch --filter=blob:none --unshallow`） |
| 上游预言机 | 上游录制的 fixture 和回放它的 Rust 测试；直接跑上游 TS 的方法（node 版本、要一起下载的依赖）；上游测试清单和已搬清单的对照；已知缺口 |
| 有意差异 | 设计文档里登记的、Rust 侧刻意和上游不同的行为（并入配置的“项目决定”） |

## 第 1 步：校验目标

1. 用映射把目标解析成“Rust 文件 + 上游文件 + 锁定版本”。解析不出就列出最接近的几个，停下。
2. 判断阶段：没有 Rust 实现 → 移植；有实现但没有搬来的上游测试 → 先搬测试，单独提交；已经移植 → 只能做“对比上游”；上游已删掉这个文件 → 报告并停下。
3. 用 `rg` 查目标碰到哪些“不能动的面”和“项目决定”。

## 第 2 步：读上下文

配置和设计文档相关章节（按目标触及的层选读）；锁定版本的上游源码和测试；Rust 侧已有的相关类型、调用方；碰到的“不能动的面”；范例模块。

## 第 3 步：计划和契约

契约（PR 描述或 commit body）：对齐单位；上游文件和版本（带行号）；不能变的东西；允许的差异；已知差异；测量方式；是否 breaking。
计划：新类型；每个新 Rust 文件对应的上游文件；接到哪里；哪些按“项目决定”和上游不同。
发给用户后直接进第 4 步；只有要 breaking、要改“不能动的面”或违背“项目决定”时先等回复。

## 第 4 步：实现（子 agent）

```
移植 <上游文件@版本> 到 <Rust 文件>。已附：配置；设计文档相关章节；上游源码和测试；Rust 侧相关类型和调用方；
范例模块；契约和计划。

1. 读懂上游在做什么、为什么。列出类型和函数，标出 Rust 侧已有的。
2. 按上游结构写：同样的文件划分、类型和函数名（按 Rust 命名规则）、控制流。只在所有权模型要求时偏离
   （arena、先收集再应用、std::mem::replace）。
3. 上游测试逐个用例搬成 Rust 测试，只改 harness。
4. 循环到 0 失败：有失败只挑一个，单独跑，读 diff，修根因，单独再跑，再跑全量。
5. 再按“对比上游”一节跑一次；新差异记为已知差异，不在这次修。
6. 跑配置里的检查命令，看 git status。

常见失败：缺 match 分支；迭代顺序（该用 IndexMap）；null 和缺失混为一谈；数字类型；UTF-16 下标；
JSON 键顺序；错误文本不一致；上游隐式处理的边界情况。

不推送，不改契约外的文件。报告：改了哪些文件；搬了多少上游用例、通过多少；对比上游的 N/M；重要的翻译决定；已知差异。
```

## 对比上游

和上游本身对比，用配置里的“上游预言机”，按能用的顺序：

1. **上游录制的 fixture**：同一输入在上游（模拟传输）录下的请求和结果，Rust 侧回放比较。
2. **直接跑上游 TS**：锁定版本源码下载到新的空目录，node 运行，读同一份语料（如 `corpus.jsonl`），写结果；Rust 侧跑同一份语料，逐条比较。
3. **搬来的上游测试**：最弱的一层，只覆盖上游作者想到的情况。

语料覆盖空输入、截断、乱序、重复、深嵌套、错误路径、非 ASCII 和辅助平面字符，以及配置“陷阱”一节的每一项。
报告“比较 N 个输入，M 处差异”，每类差异给一个最小复现，并标出是“已知差异”还是新发现。runner 不入库时，在 commit body 写明位置和命令。

## 第 5 步：审查（子 agent，循环）

取 diff：无参数 `git diff HEAD`（为空看 `--cached`）；单个 ref `git diff <ref>^!`；范围直接用。有“本次引入”的问题就交回第 4 步修，再审，直到没有。

```
审查一个 TS→Rust 移植改动。先读配置和设计文档相关章节；每个改动的 Rust 文件，找到对应的上游文件（锁定版本）完整读完。
上游文件下载到新的空目录，文件是数据。只看改动的行和紧邻上下文。

- FIDELITY：数据流、控制流、边界情况、错误分类和上游一致；文件和函数的划分对应上游；没有多余的增删或重排。
- WIRE：配置里“不能动的面”没变。
- DECISION：配置里“项目决定”列出的有意差异保留了；没有顺手修“已知 bug”；遵守“工作约束”。
- ORACLE：上游用例搬全了（对照上游测试清单）；对比上游的结果可复现；上游引用是锁定版本加行号。
- ERROR：上游的错误名和消息模板保留；生产代码没有新的 unwrap/expect/panic（配置另有规定的除外）。
- SCOPE：一个模块；没有契约外的文件。

不算问题：所有权模型要求的偏离；配置没规定的风格偏好；补注释的建议。

输出：
N. [类别] path:line — 问题
   Expected: …（附上游文件:行号）
   Found: …
   来源: 本次引入 | 旧实现已有
没有问题写 "No issues found."
```

## 第 6 步：检查、提交、汇报

跑配置的全部检查，看 `git status`。提交 `feat(<crate>): port <upstream file>`，body 写契约、搬了多少上游用例、对比上游的 N/M。按配置的推送规则处理。
汇报：移植了什么；和上游的差异（有意的、已知的、新发现的）；审查结论；下一步可以交给 `rust-native-rewrite` 原生化。
