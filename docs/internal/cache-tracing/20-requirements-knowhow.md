# 缓存审计:需求方视角与需求清单(know-how)

> 本文件只记录"谁、为什么、需要什么"。设计另起,等需求确认后再做。
> 来源:深度调查(D3/D4 真实案例)+ 与需求方讨论。Date: 2026-08-01

---

## 一、需求方角色

### 角色 A:开发者(写 agent / 集成 aimux 的人)

他在写多轮 agent 或 RAG,跑起来发现"比预期贵""比预期慢"。他能改的是自己的代码(prompt 结构、消息组织、工具定义),改不了服务端。

**他最痛的不是"服务端有没有掺水",而是"我的 agent 设计是不是在自毁缓存"。**

### 角色 B:使用者(跑生产的运维/成本负责人)

他在线上跑 aimux,关心钱、稳定性、供应商可信度。他改不了 prompt,但能换供应商、换网关、调预算。

**他最痛的是"账单对不上"和"供应商悄悄变了",而且往往要亏了几百块、跑了几个月才发现。**

### 两者的关键差异

| 维度 | 开发者(A) | 使用者(B) |
|---|---|---|
| 时间尺度 | 单次会话、单次改动(A/B) | 周/月趋势、事故回放 |
| 主要敌人 | 自己的 prompt 设计 | 供应商/网关的不可信 |
| 核心动作 | 定位并修复前缀破坏点 | 检测并取证异常漂移 |
| 单点掺水判定 | 不太关心(修不了服务端) | 关心,但要趋势才信 |
| granularity | 到字段、到行 | 到 provider、到时段 |

## 二、开发者(角色 A)的需求

### A1. 前缀稳定性诊断

跑一个 agent 任务,开发者第一想知道:**我的前缀到底稳不稳定,如果不稳定,在哪断的。**

| 需求 | 说明 |
|---|---|
| A1.1 分叉点定位 | 相邻请求对比,前缀在第几块、对应哪个语义段(system / tools / 第 N 条消息 / reasoning)开始不一样 |
| A1.2 段位稳定性 | system 段、tools 段、conversation 段各自是否在会话内稳定(字节级) |
| A1.3 动态内容暴露 | 检测 system/tools 里的动态内容(时间戳、随机 ID、用户个性化)——这些是"看起来没变实际变了"的元凶 |

**真实案例(为什么需要)**:
- TradingAgents 0% 命中率,根因是 system prompt 塞了 `current_date`/`instrument_context`,从第一个 token 就变,白付 30-40%。**服务端只报"命中 0",不会说"你的 system 第 3 行有个时间戳在动"**
- openclaw 143 次调用 cacheRead 仅 10.5%,根因是 60-120KB system 里混了动态"当前时间/workspace 状态/heartbeat"。整块打 cache_control → 精确匹配必然失败

### A2. 命中归因

某一轮没命中,开发者想知道**为什么没命中**,而不是只看到一个"0"。

| 需求 | 说明 |
|---|---|
| A2.1 breaking change 归因 | 是 breaking change 导致的(哪段变了:system/tools/历史压缩/模型切换),还是 TTL 过期,还是路由到不同机器 |
| A2.2 reasoning 漂移检测 | reasoning content 回填进下一次历史时是否在两次请求间漂移(流式截断/max_tokens 截断/stop/不同 effort 生成不同长度)→ 隐蔽的 breaking change 源 |
| A2.3 合法 miss 白名单 | 预热期、DeepSeek 64 单元粒度、GPT-5.6+ implicit 断点、低于门槛——这些 0 命中是合法的,不该报警 |

**为什么需要**:开发者改完 prompt 拆分后,要确认"这一轮没命中是因为我改对了(动态部分移走了)还是改坏了(把稳定的也动了)"。没有归因,他就只能盲改。

### A3. 改动验证(A/B)

| 需求 | 说明 |
|---|---|
| A3.1 改动前后命中率对比 | 同一会话/同一任务,改动前后的命中率、命中段位分布对比 |
| A3.2 段位命中分解 | 不只给总 claimed,而是按 system/tools/conversation 三段分别给"该段是否稳定 + 该段命中数" |
| A3.3 预期节省 vs 实际节省 | 改动预期能省多少 token,实际省了多少 |

### A4. 会话级账本

| 需求 | 说明 |
|---|---|
| A4.1 任务级 token 账本 | 整个 agent 任务的:实际付的 token / 假设全命中的 / 假设全不命中的 |
| A4.2 命中数演化曲线 | 命中数随轮次的变化,标注每轮的 breaking change |
| A4.3 冗余量化 | agent loop 每轮重发全量历史,5 次工具调用任务典型 71% token 冗余——让开发者看到"冗余了多少,缓存救回多少" |

## 三、使用者(角色 B)的需求

### B1. 供应商可信度监测

| 需求 | 说明 |
|---|---|
| B1.1 上报 vs 客户端上界的长期偏离 | 服务端上报的命中数 vs 客户端独立算的上界,不是单次而是趋势(周/月) |
| B1.2 命中率时间序列 + 漂移检测 | 某天突然掉了 → 可能是供应商改了 TTL/路由/模型权重(Anthropic TTL 静默回归就是 11.9 万次调用比对才发现的) |
| B1.3 异常分级 | 单次超 LCP(高置信掺水)、usage 与账单漂移(中)、TTFT 不随命中率改善(低,旁证) |

**真实案例(为什么需要)**:
- OpenAI 2025-01:API 报 90% 命中,账单几乎没打折,多收 1.7×,用了几个月才发现
- Anthropic 2026-03:TTL 1h→5m 静默回归,成本涨 20-32%,官方没公告
- 中转网关"命中仍按全价收用户"——掺水动机模型,用户看不到

### B2. 成本异常预警

| 需求 | 说明 |
|---|---|
| B2.1 早期预警 | 在亏了几百块之前发现命中数不对劲(漂移检测,不是事后对账) |
| B2.2 实际 vs 应付差值累计 | 实际付的 token vs 按 claimed 命中应该付的 token 的差值,长期累计 |
| B2.3 事故回放 | 故障时段的 trace 回放——是命中掉了、重试多了、还是某次 breaking change 清空了缓存 |

### B3. 供应商/网关选型

| 需求 | 说明 |
|---|---|
| B3.1 多供应商对比 | 直连 vs OpenRouter vs LiteLLM vs Portkey,谁的命中上报更可信(A/B/C 级) |
| B3.2 网关透传完整性 | 网关有没有剥字段(Portkey 流式剥 cached_tokens、vLLM V1 恒 null、Ollama 恒 0) |
| B3.3 响应缓存 vs prompt 缓存区分 | OpenRouter/LiteLLM 的响应级缓存(usage 归零)是第二类合法缓存,别误判为漏报 |

## 四、两类角色共享的需求

| 需求 | 说明 |
|---|---|
| C1 零侵入开关 | 库性质,默认零开销,显式开启才采集;不破坏现有 API |
| C2 不存明文 | 请求体含用户数据,只存哈希指纹;满足隐私约束 |
| C3 跨语言可用 | 8 语言绑定都能拿到 trace 数据(开发者用 Node/Python,使用者可能用 Go/Java 跑服务) |
| C4 离线重跑 | trace 可导出(JSONL),离线重新跑全部审计规则,不必在线实时判 |
| C5 取证格式 | 出问题时要能拿出证据(规则 id、期望区间、命中的历史请求 id)给供应商/内部对账 |

## 五、需求优先级(初步,待确认)

按"解决最痛的问题"排序:

| 优先级 | 需求 | 服务谁 | 理由 |
|---|---|---|---|
| P0 | A1.1 分叉点定位 + A1.2 段位稳定性 | 开发者 | 开发者最痛、最高频;没有它开发者只能盲改 prompt |
| P0 | A2.1 breaking change 归因 + A2.2 reasoning 漂移 | 开发者 | "为什么没命中"是开发者改 prompt 的前提 |
| P0 | B1.2 命中率时间序列 + 漂移检测 | 使用者 | 使用者最痛;早一天发现就少亏一天 |
| P1 | A3 改动验证(A/B) | 开发者 | 依赖 P0 的数据,是 P0 的自然延伸 |
| P1 | B1.1 上报 vs 上界长期偏离 + B2 成本预警 | 使用者 | 趋势判定,依赖时间序列积累 |
| P1 | A4 会话级账本 | 开发者 | 量化"省了多少",依赖段位命中分解 |
| P2 | B3 供应商选型 | 使用者 | 低频但高价值;依赖多供应商数据积累 |
| P2 | C5 取证格式 | 共享 | 出事才用,但出事时必须有 |

## 六、待确认问题

1. **开发者 vs 使用者的产品形态是否分离?** 开发者要的是"单会话诊断报告",使用者要的是"长期监测面板"。是一个子系统两种视图,还是两个独立功能?
2. **reasoning 漂移检测的深度**:只检测"reasoning 段在两次请求间是否字节一致",还是要语义级判断(同一问题不同表述)?后者成本高很多。
3. **B2 成本预警需要真实价格表**:aimux 是否维护各 provider 的计费倍率(读 0.1×、写 1.25× 等)?还是只给 token 数,让用户自己算钱?
4. **A3 A/B 对比的基准**:改动前后的会话如何对齐(同一任务重跑?同一 prompt 集?)?这决定对比是否有意义。
5. **段位分解的粒度**:system/tools/conversation 三段够不够?conversation 段要不要再细到"第 N 轮 assistant/user"(reasoning 单列)?
